# CTC CLI Report Generator — Antigravity Refactoring Plan

Repository: [chaziyu/cli-report-generator](https://github.com/chaziyu/cli-report-generator?utm_source=chatgpt.com) Objective: Simplify the existing application into a single-page workflow without rewriting its working processing engine.

Target workflow: Copy CLI commands → Upload PuTTY log and Word report → Paste or drop GUI screenshots → Generate → Review → Download.

## Target user experience

1\. CLI Commands

Copy individual approved commands into customer's PuTTY

2\. Upload Evidence

PuTTY TXT + existing CTC DOCX + GUI screenshots via paste/drop

3\. Generate

Parse, evaluate, render CLI evidence and prepare document changes automatically

4\. Review

Show all findings; prioritize missing, failed and uncertain checks

5\. Download DOCX

Original CTC report layout preserved

The engineer should not have to create a session manually, configure device records, parse logs separately, generate evidence separately or open an export configuration dialog.

## Phase 3: Add GUI screenshot paste and drag-and-drop

Objective: Allow engineers to add GUI screenshots without saving and uploading each one manually.

Existing code to modify

- `src/components/session/session-workspace.tsx` — Existing file upload handling.
- `src/app/api/sessions/[id]/files/route.ts` — Existing upload API.
- `src/lib/storage/types.ts` — Already includes a `screenshots` storage category.
- `prisma/schema.prisma` — `UploadedFile.type` already supports `GUI_SCREENSHOT` as a documented value.
- `src/vendors/fortigate/checklist.ts` — Already distinguishes `GUI_MANUAL` checks.

New code proposed

- `src/components/evidence/gui-screenshot-uploader.tsx`
- `src/components/evidence/screenshot-card.tsx`
- `src/core/evidence/gui-evidence-mapper.ts`
- A screenshot-specific API route only if the existing file endpoint cannot support the required metadata safely.

### Required behavior

Support three input methods:

1. `Ctrl+V` to paste a screenshot copied from the customer's screen.
2. Drag and drop PNG/JPEG screenshots.
3. Choose multiple image files.

After receiving a screenshot:

- Save it automatically.
- Display a thumbnail.
- Suggest a checklist/appendix destination where possible.
- Allow changing that destination.
- Allow removing or replacing the screenshot.
- Preserve original image data.

### FortiGate screenshot mapping

| GUI task             | Default appendix             |
| -------------------- | ---------------------------- |
| GUI Accessibility    | Appendix 9                   |
| Backup Configuration | Appendix 16                  |
| Other manual checks  | Engineer selects destination |

The app should use the selected vendor's report layout, not hardcode these appendix numbers throughout the UI.

Important: The customer may have completed the GUI screenshot before or after the CLI checks. Screenshot upload must not depend on the PuTTY log already being processed.

### Clipboard handling

- Listen for paste events only when the screenshot upload area is active or focused.
- Detect image data on the clipboard.
- Ignore ordinary text pastes.
- Convert clipboard image data into a supported file.
- Preview the image immediately.
- Show a clear error if clipboard access is unavailable.
- Avoid globally intercepting `Ctrl+V` while the engineer edits remarks.

### Appendix insertion rules

- One appendix may contain multiple screenshots.
- Existing images must not be deleted automatically.
- The engineer must approve replacing existing appendix evidence.
- If a screenshot has no confirmed destination, leave it unmapped and flag it.
- Manual screenshot evidence should retain its original identity, separate from generated CLI images.

Validation

- Paste PNG screenshots from the clipboard.
- Drop multiple screenshots.
- Reassign an image from Appendix 9 to Appendix 16.
- Reject invalid files.
- Persist images after page refresh.
- Ensure images are not attached to the wrong firewall in multi-device sessions.

## Phase 4: Build automatic processing orchestration

Objective: Replace separate Parse, Evaluate and Generate Evidence actions with one primary button.

Existing endpoints to reuse

| Endpoint                                         | Current function                         |
| ------------------------------------------------ | ---------------------------------------- |
| `src/app/api/sessions/[id]/parse-log/route.ts`   | Parses uploaded logs                     |
| `src/app/api/sessions/[id]/evaluate/route.ts`    | Evaluates checklist results              |
| `src/app/api/sessions/[id]/evidence/route.ts`    | Generates CLI evidence                   |
| `src/app/api/sessions/[id]/inspect-doc/route.ts` | Inspects Word structure                  |
| `src/app/api/sessions/[id]/review/route.ts`      | Retrieves findings and records decisions |

New code proposed

- `src/core/workflow/report-pipeline.ts`
- `src/core/workflow/workflow-status.ts`
- `src/app/api/sessions/[id]/process/route.ts`

### Processing sequence

After the engineer clicks Generate PM Report:

1. Validate uploaded files.
2. Create or resume the PM session.
3. Inspect Word metadata, sections and devices.
4. Map PuTTY logs to devices.
5. Parse recognized CLI commands.
6. Evaluate checklist results.
7. Generate CLI evidence images.
8. Associate manually uploaded GUI screenshots.
9. Compare proposed findings with original Word values.
10. Prepare the review screen.

This button should prepare the report, not silently finalize unsupported findings or overwrite original evidence.

### Failure handling

Each operation must report its own status.

For example, if parsing succeeds but evidence generation fails, the engineer should be able to retry evidence generation without uploading everything again.

Design the pipeline to be:

- Idempotent where possible.
- Safe to retry.
- Able to retain successful intermediate results.
- Resistant to duplicate evidence and checklist records.
- Explicit about partially completed processing.

The current evidence endpoint deletes prior evidence records for a command before regeneration. Review that behavior carefully so new GUI screenshots and engineer-approved evidence are never accidentally deleted.

Do not change: Existing parser, evaluator and renderer algorithms unless integration testing reveals a specific defect.

Validation

- One button initiates the required processing stages.
- Processing errors are visible.
- Retrying does not create duplicate results.
- Incomplete logs remain reviewable.
- The UI never claims the report is complete when mandatory processing failed.

### Required changes

Prepare the report automatically after analysis, but apply only approved findings and evidence modifications when exporting.

Replace the routine export modal with a visible primary Download button.

The export operation should:

- Use the uploaded Word file.
- Apply approved checklist updates.
- Insert approved CLI evidence.
- Insert approved GUI screenshot evidence.
- Preserve original content unless replacement is approved.
- Preserve sign-off sections.
- Validate the resulting DOCX.
- Produce a change summary.

### Existing-report preservation

Do not regenerate the entire CTC Word report. Use targeted OOXML changes to maintain its existing layout.

Special care is required for:

- Word tables and merged cells.
- Existing screenshots.
- Appendix headings.
- Checkboxes.
- Headers and footers.
- Signatures.
- Page numbering.
- Table of contents.

Do not change: The original uploaded document or protected authorization sections.

Validation

- The generated Word report opens without repair warnings.
- GUI and CLI evidence appears in the intended appendices.
- Original screenshots remain unless replacement was approved.
- Report formatting is visually consistent with the source.
- Unsupported layouts fail safely with an explanation.

### Final acceptance criteria

The refactor is complete when an engineer can:

1. Open the homepage directly.
2. Copy FortiGate commands without leaving the page.
3. Upload a PuTTY TXT log and existing Word report.
4. Paste GUI screenshots using `Ctrl+V`, or drag and drop them.
5. Click Generate PM Report once.
6. Review the results, focusing on exceptions.
7. Download the updated CTC Word report without navigating through multiple workspaces.

Future vendors must use the same frontend workflow. Only their command definitions, parsers, validation rules and report mappings should differ.


## Implementation process

Before implementation, inspect and trace the actual existing code.

Follow the ten phases in the agreed implementation plan, respecting dependencies.

For each phase:

- Identify exact existing code to modify.
- Identify new files and functions to add.
- Preserve existing architecture and reusable logic.
- Make the smallest required changes.
- Add relevant tests.
- Run tests, linting, type checks and builds.
- Report changed files, validation results and unresolved risks.

Do not perform unrelated refactoring or cleanup.

Do not proceed to the next phase until the current phase is validated.

Start by preparing an exact code-level plan for Phase 1. Do not modify code until the plan is reviewed and approved.

Recommendation: Treat this as a simplification of the existing application, not a new project. The current backend already provides much of the required functionality. The priority is to consolidate those capabilities into one predictable, engineer-friendly workflow while adding reliable GUI screenshot handling.
